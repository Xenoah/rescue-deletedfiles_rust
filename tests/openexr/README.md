# Native OpenEXR references

The OpenEXR C++ 3.5.4 Python binding and FFmpeg generated these flat HDR images from numeric samples. The manifest records each file SHA-256, producer, dimensions, type and decoded pixel SHA-256 for every named channel. Channel digests cover little-endian pixel values in row order, including arbitrary channels such as object ID and depth.

The recovery test writes and reads each original on FAT32 and ext4, deletes it, and compares the recovered bytes and SHA-256 in ordinary and indexed carving. On Linux it also decodes every recovered channel with OpenEXR. The portable suite uses the stored files without requiring the native decoder. For regeneration, run `python tests/openexr/generate.py /path/to/empty-directory` with OpenEXR, NumPy and FFmpeg installed.

Five multipart fixtures include stereo views, a cropped part with a negative data-window origin, mixed tiled and scan-line parts, four named parts, and physically interleaved chunks. The independent OpenEXR reader decoded exactly the same pixels from the stereo source and its reordered copy. All 22 files were recovered from FAT32 and from ext4 with 4 KiB blocks. On an additional 1 KiB ext4 volume, debugfs stored both stereo files with sparse holes. Raw carving declined those candidates. Rescue's filesystem command used The Sleuth Kit and surviving extent metadata to restore the holes as zeros; both files and their decoded channel values matched the originals.

A further five fixtures use the OpenEXR SDK's `exrmaketiled` to create MIP and RIP pyramids. They cover floor and ceiling rounding, rectangular tile edges, half/float/unsigned channels and ZIP/PIZ/PXR24/B44 compression across 136 level combinations. `generate_levels.py` and `read_levels.cpp` record an independent SHA-256 for each channel at each level. On Linux the native test builds that small OpenEXR SDK reader and checks every recorded level again after recovery. Regeneration requires the SDK tools, C++ headers/compiler and pkg-config. The portable recovery executable has no SDK dependency.
