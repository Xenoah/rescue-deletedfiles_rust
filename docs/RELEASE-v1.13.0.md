# Rescue v1.13.0

Btrfsで削除前の読み取り専用スナップショットが残っていれば、GUIとCLIから過去のファイルを復元できます。元の拡張子や削除前のハッシュを用意する必要はありません。単一デバイスのボリュームRAWを直接読み取ります。

## GUIでの復元

1. 設定の「保存済みイメージ」でBtrfsボリュームのRAWを選びます。
2. 「ディスクのツール」から「Btrfsスナップショットから復元」を開きます。
3. 現行サブボリュームと過去のスナップショットを選び、「過去にだけ存在するファイルを表示」を押します。
4. 保存先フォルダーを選び、指定したファイルまたはすべての候補を復元します。出力名にはスナップショットとinodeの番号が入ります。結果には元のパス、保存先、個別の失敗が表示されます。

CLIでは最初にサブボリューム番号を確認します。次の番号は検証用ボリュームの例です。

```sh
rescue btrfs --source volume.raw --json
rescue btrfs --source volume.raw --current-root 256 --snapshot-root 257 --json
rescue btrfs --source volume.raw --current-root 256 --snapshot-root 257 --all --destination recovered --json
```

## 実ファイルでの検証

Linuxカーネルで作った6個のボリュームを使いました。各ボリュームで元ファイルを書き込み、読み取り専用スナップショットを作り、現行のパスを削除しました。復元後に各ファイルのバイト列とSHA-256を原本と照合しました。

| 検証対象 | 結果 |
| --- | --- |
| インラインデータ | PNG・XML・TXT・ZIP・MP3・RTF・WebPの7件が無圧縮とzlibの両方で一致。Linuxがセクター末尾をゼロで埋めて圧縮したファイルも復元 |
| 通常のデータ領域とスパースファイル | UTF-8テキスト・CSV・BMP・WAV・ZIP・独自バイナリ・1 MiBの穴があるファイルの7件が、zlibとZstandardの両方で一致 |
| LZO、共有領域、事前割り当て | LZOとZstandardの各13件が一致。元の領域の8192バイト目から49152バイトを共有するファイル、未書き込み領域、空ファイルを含む |
| GUI操作 | LZOのスナップショットで指定した2件と、全候補13件をそれぞれ別フォルダーに復元。全出力と原本が一致し、復元元のSHA-256も保持 |
| 破損時の動作 | DUPメタデータの片方を壊した場合はもう一方から7件を復元。両方の破損は検出。別の試験で1ファイルのデータセクターを壊すと、該当ファイルのチェックサムエラーを報告し、残る6件を原本どおりに保存 |

[GUIの照合結果と画面](gui-v1.13-results.json) · [インラインの検証](../tests/btrfs-reference/README.md) · [データ領域の検証](../tests/btrfs-large-reference/README.md) · [LZO・共有領域の検証](../tests/btrfs-lzo-reference/README.md)

標準の統合試験は63群です。別の35形式・36原本による試験では、管理情報があるNTFS・FAT32・exFATなどの8条件でCLIとMCPの576件すべてが一致しました。管理情報を消した連続配置は31/36件、断片化配置は11/36件、全体を上書きした場合は0/36件でした。

## 対応条件

Btrfsの経路はボリューム先頭のRAW、CRC32C方式、singleまたはDUP配置を扱います。スーパーブロック、ツリーブロック、通常のファイルデータに記録されたチェックサムを照合します。対象は過去に存在し、現行ツリーから消えた通常ファイルのパスです。移動や名前変更で消えた旧パスも含みます。

複数デバイスのRAID、別のチェックサム方式、データチェックサムを省略した通常ファイルは、対応するLinuxカーネルなど別の読み取り手段が必要です。削除前のスナップショットが残っていなければ、この方法で過去の内容は取得できません。ディスク全体が上書きされた場合や、TRIMによって元のバイト列が失われた場合も復元できません。[入力形式と外部ツール](IMAGING.md)
