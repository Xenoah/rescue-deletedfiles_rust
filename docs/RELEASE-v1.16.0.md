# Rescue v1.16.0

ext4でファイルを削除した後、現在のinodeからサイズと配置が消えていても、内部ジャーナルに削除前の管理情報が残っていればファイルを取り出せます。事前に記録した配置表やスナップショットは不要です。

## GUIとCLIでの手順

GUIの「設定」でext4ボリュームのイメージを選び、「ディスクのツール」から「ext4ジャーナルから復元」を開きます。候補を選び、新しい保存先ファイルと原本のSHA-256を入力します。原本ハッシュがない場合は、その旨を明示して未照合の内容を保存できます。

```sh
rescue ext4-journal --source volume.raw --json
rescue ext4-journal --source volume.raw --inode 13 --output recovered.bin --sha256 ORIGINAL_SHA256 --json
rescue ext4-journal --source volume.raw --inode 13 --output recovered.bin --allow-unverified-content --json
```

候補にはinode、サイズ、inodeの世代、管理情報を見つけたジャーナルのトランザクション番号を表示します。同じトランザクションでディレクトリとinodeを結び付けられた名前は、親ディレクトリのinodeと元の名前の生バイトも併記します。保存前に、現在の割り当て情報と過去の管理情報を照合します。

## 削除した実ファイルでの検証

| 試験 | 結果 |
| --- | --- |
| 1 KiB・4 KiBブロックのext4 | LinuxでTXT、CSV、BMP、WAV、ZIP、独自バイナリ、スパースファイルを実際に削除。2ボリュームで各7件を復元し、原本ハッシュを指定した14件と、ハッシュなしで保存後に照合した14件のすべてで全バイトとSHA-256が一致 |
| inodeに収まらない配置 | 別の2ボリュームで、WAV、BMP、PGM、PPM、ZIP、TAR、独自バイナリを削除。Linuxのfilefragで各ファイルが16～17個のエクステントに分かれていることを確認。外部のエクステントツリーをジャーナルから読み、14/14件が原本と一致 |
| GUIでの復元 | 外部ツリーを使う7件を候補から個別に保存し、7/7件の全バイトとSHA-256が一致。原本ハッシュを指定した6件、明示的に未照合で保存した1件を独立して再照合。別の原本のSHA-256を入力した試験では出力を拒否 |
| 破損と再利用 | ジャーナル・inodeの管理情報、ディレクトリまたはエクステントツリーのチェックサム不一致を検出。実際にデータブロックを再割り当てした試験では元の配置からの復元を拒否。空き領域の1セクターを変更した試験では、原本ハッシュ指定時に不一致を検出 |

## 復元条件

単一のext4ボリュームを読み取ります。確認したのは64ビットのグループ記述子、メタデータチェックサム、チェックサムv3の内部JBD2ジャーナルを使うLinuxイメージです。内部ジャーナルの上限は256 MiBです。過去のトランザクションが循環で失われた場合、必要なエクステントツリーが残っていない場合、inodeやデータブロックが再利用された場合は、この経路では復元できません。

通常のext4はファイル内容のチェックサムを持ちません。空き領域に別のデータが書かれた場合でも、元の配置から同じサイズのファイルを取り出せることがあります。原本の照合には独立したハッシュが必要です。復元機能は内蔵で、e2fsprogs・Linuxカーネル・filefragはイメージ作成と独立検証に使用しました。[コマンドと対応条件](IMAGING.md)
