# dcfldd・dc3ddの分割取得から復元する

v1.24.0の公開Linux版を使い、Windowsで7ファイルを実際に削除した96 MiBのNTFS参照イメージを、dcflddとdc3ddで6通りに取得しました。各組で結合したディスク全体を元イメージとバイト単位で比較し、取得ソフトが記録した全セグメントのSHA-256、Windowsで記録した全体SHA-256、復元した7ファイルの全バイトとSHA-256を照合しました。

| 取得ソフトと指定 | 先頭・末尾 | 分割数 | Rescueへの指定 | 復元 |
| --- | --- | ---: | --- | ---: |
| dcfldd 既定 | .000〜.047 | 48 | 先頭を指定 | 7/7 |
| dcfldd `splitformat=%04d` | .0000〜.1029 | 1,030 | 先頭を指定 | 7/7 |
| dcfldd `splitformat=WIN` | .001〜.032 | 32 | 先頭を指定 | 7/7 |
| dcfldd `splitformat=MAC` | .dmg、.002.dmgpart〜.024.dmgpart | 24 | 最初に.dmg、続く全ファイルを番号順に指定 | 7/7 |
| dc3dd `hofs=evidence.1111` | .0001〜.0020 | 20 | 先頭を指定 | 7/7 |
| dc3dd `hofs=evidence.aaa` | .aaa〜.abf | 32 | 全ファイルを文字順に指定 | 7/7 |

インポートには `--image-type raw` を選び、元ディスクの長さとSHA-256を渡しました。MACの行はdcflddが作成した生バイトの分割セットです。Apple UDIF形式のDMGには専用の読み取りが必要です。Rescueのプロセスでは外部ツールの検索パスを空にし、同時に開けるファイル数を64に制限しました。

## 3桁を使い切った取得の実測

今回のdcfldd 1.9.2では、1区画97,792バイトで1,030区画を書き込む際に、既定の3桁の名前を1,000区画で使い切りました。取得コマンドは正常終了し、入力全体のSHA-256は正しく記録されましたが、保存先には1,000ファイルだけが残りました。先頭30区画のファイル名が再利用され、最後の短い区画の後ろには旧区画の62,464バイトが残っていました。残ったファイルの合計は97,792,000バイトで、原本は100,663,296バイトです。

Rescueは取得時の長さの照合と、元ディスクのSHA-256の照合のどちらでも不一致を検出し、結合結果を出力しませんでした。同じディスク・区画サイズで、取得前に4桁を指定した例では1,030区画すべてが残り、7ファイルを復元できました。取得後に末尾のファイルが欠落した場合も、判定には元のサイズやハッシュが必要です。

独立した取得と再現にはdcfldd、dc3dd、QEMUを使用します。実行にはLinux、Python 3.11以降、および各コマンドが必要です。[ファイル別・取得方式別の実測値](forensic-split-v1.24-results.json)

```sh
python scripts/e2e_forensic_split_sets.py --binary /path/to/rescue --evidence results.json
```
