# Rescue v1.43.0

SVGと、gzipで圧縮されたSVGZを、削除後も連続して残っているディスク領域から復元できます。UTF-8、BOM付きのUTF-16LEとUTF-16BEに対応します。GUIではCarvingを選びます。CLIでは次のように検索してから別のディスクへ書き出します。

```sh
rescue scan --source disk.raw --work-dir scan --mode carve --extension svg --extension svgz --json
rescue recover --session scan/<session>.rescue-session.json --all --destination restored --json
```

## 実ファイルの復元結果

InkscapeとCairoの出力を含む16件のSVGと、それぞれを圧縮した16件のSVGZを準備しました。長さ・SHA-256・描画後の画素を記録し、各原本をFAT32とext4に書き込んで読み戻した後、mtoolsとdebugfsで実際に削除しました。Unicodeの補助文字が読み取り境界をまたぐ原本も含みます。[原本と再現手順](../tests/svg/README.md) · [各原本のSHA-256](../tests/svg/manifest.json)

| 復元方法 | FAT32 | ext4 |
| --- | --- | --- |
| 通常および索引付きの内容検索 | 30件が全体一致、2件が閉じタグまで一致 | 30件が全体一致、2件が閉じタグまで一致 |
| ファイルシステムが記録した長さを使用 | 32件の全バイトとSHA-256が一致 | 32件の全バイトとSHA-256が一致 |
| 原本と復元物を独立に描画 | 全32件の32×24 RGBA画素が一致 | 全32件の32×24 RGBA画素が一致 |

閉じタグで止まった2件はCairo・Inkscapeが末尾に改行を付けたSVGです。FAT32で全長を確定した32件のうち25件は単一クラスタで、7件は明示的な連続配置の推定を使用しました。ext4ではThe Sleuth Kitを使用しました。Ubuntu 22.04向けのlibrsvg 2.52.5とDebianの2.60.0のそれぞれで原本と復元物の画素が一致しました。v1.42.0でXML・gzipとして保存した両ディスクの候補20件も、元のセッションから以前と同じバイト列で復元できました。[復元方法別の照合記録](svg-native-results.json)

LinuxのGUIで、FAT32から削除した16件のSVGZを選択してZIPに復元しました。展開した3,790バイトを原本と直接比較し、画面から保存したHTML・CSVをZIP内の復元記録と照合しました。[GUIの記録と8枚の画面](gui-v1.43-results.json)

Rustテスト96件とClippy、Linuxリリース実行ファイルの統合試験102組が通過しました。35形式・36原本による回帰試験では1,116条件が期待結果と一致し、1,016条件で原本の全バイトに一致しました。

## 破損と対応範囲

- XMLの要素・属性・名前空間、Unicodeの妥当性、SVGZのgzipメンバー終端・CRC32・展開長を照合します。異なる名前空間、壊れたサロゲート、宣言と実際のバイト順の不一致、壊れた圧縮データ、読み取り不能範囲など49条件で該当候補を拒否しました。ファイル直後から読み取り不能な場合はSVG・SVGZの両方が全体一致しました。構造を保った色の変更は、元のSHA-256との照合で区別できました。[条件別の結果](svg-results.json)
- プレーンSVGの内容検索には、対応するXML宣言またはSVGの開始タグから閉じタグまでの連続したデータが必要です。末尾の空白・コメントの所属や飛び離れた断片の順番を確かめるには、ファイルシステムの記録などが必要です。SVGZでは検証できた単一gzipメンバーを取り出します。
- XMLの上限は8 MiB、入れ子は256段です。DTD、外部エンティティ、BOMのないUTF-16は対象外です。復元処理はSVG中のスクリプトを実行せず、リンク先も取得しません。描画確認にはlibrsvgなどの外部ソフトが必要です。ファイル自体の復元はRescueの内蔵機能で行えます。
- 既に上書き・TRIMされた領域は、別の世代やコピーに元のデータが残っていない限り復元できません。
