# Rescue — 製品仕様案

仕様版: 0.3

状態: 対象範囲と性能優先順位はユーザー確認済み。具体設計はレビュー用。

更新日: 2026-11-04（日本時間）

## 1. ユーザーから確定している要件

- 完全削除されたファイルを復元するソフトウェア。Windowsに加えLinux・macOSにも配布する。
- Rustで構築する。
- GUI、CLI、MCPの3つの操作方法を提供する。
- 有料の復元ソフトを上回る性能を目指す。
- 開発の区切りごとにGitHubへpushし、リリースする。
- 実装の前に仕様を固める。
- NTFS、exFAT/FAT32、SDカード・USBメモリ、破損ディスク、RAIDのすべてを対象にする。
- 最も重視する性能は「復元できるファイルの多さと内容の完全性」とする。
- 既定はExplorer風の詳細ビュー。名前、作成日時、更新日時、種類、サイズを列で表示し、並べ替え・グループ化に対応する。アイコン表示へも切り替えられる。
- 操作は「起動 → 保存方式と詳細検索の設定 → スキャン → 復元ファイルの選択 → 復元」。保存方法は任意のフォルダーまたはZIP。
- 今後のリリースはWindows・Linux・macOSそれぞれのインストール版とポータブル版を必須とする。
- README・リリースに実際のスクリーンショットと技術説明のインテリジェンスUIを毎回掲載する。

以下の設計と数値は提案であり、実装済み機能や達成済み性能を示さない。
仮称をRescueとする。ライセンスはユーザー指定によりMIT。正式名称、販売・配布形態は未決定。

## 2. 製品の目的と「完全削除」の定義

ごみ箱を空にした、Shift+Deleteした、通常のファイル一覧から消えたファイルを対象とする。
ファイルシステムの管理情報や記憶媒体に残るデータを読み取り、別の保存先へ取り出す。

データが残っている「論理削除」と、上書き・消去済みの状態を区別する。
上書き、Secure Erase、暗号鍵の喪失、SSDのTRIM後などで読み出せる元データが
失われている場合、その元データを復元できると約束しない。
TRIM対応SSDでも、コマンド対応の有無だけで復元不能と断定しない。
ゼロ埋めの読み出しも、TRIMが原因であると断定する根拠にはしない。

AIによる補完やファイル修復は、元のバイト列を取り出す「復元」と分ける。
初版はデータを推測生成しない。後から修復機能を追加する場合も、復元物を残し、
修復物には別名と処理履歴を付ける。

## 3. 優先順位とリリース範囲

元データへの非破壊性を必須条件とし、性能の最優先は内容の完全性と復元率とする。
名前・階層の再現、処理速度、操作性も評価する。
対象をNTFSだけに限定せず、以下の全カテゴリをv1.0の必須範囲とする。
開発と検証は段階的に進めるが、初期の開発版を全機能版として扱わない。

### 3.1 初期の開発版 v0.1

- Windows 11 x64を主対象とする。
- RAW形式のNTFSボリュームイメージを入力にする。
- 削除済みMFTレコードから、非圧縮・非暗号化の通常ファイルを復元する。
- resident DATAとnon-resident DATAを扱い、runlistに従って断片化を復元する。
- CLIでスキャン、候補一覧、選択復元、結果レポートを提供する。
- 同じエンジンを使うGUIとローカルstdio MCPを提供する。
- 合成イメージで正解ハッシュとの一致と、入力の無変更を検証する。

v0.1は機能確認用のプレリリースとし、実ディスク対応や競合優位性を宣伝しない。

### 3.2 初回安定版 v1.0

| 分類 | 必須範囲 |
| --- | --- |
| OS | Windows x64、Linux x64、macOS x64 / arm64。最低OSと実行検証環境を版ごとに明記 |
| 入力 | Windowsの論理ボリューム、物理ディスク、RAWイメージ |
| パーティション | MBR/GPTの検証、失われた領域の探索と仮想的な復元 |
| NTFS | 削除ファイル、resident/non-resident、runlistによる断片化、属性リスト、疎ファイル、LZNT1圧縮、ADSの別ファイル保存 |
| FAT32/exFAT | 削除ディレクトリエントリー、残存クラスターチェーン、exFATの連続割当、管理情報が失われた場合のcarving |
| 外部媒体 | USB接続HDD/SSD、USBメモリ、SDカード。接続方式とファイルシステムを別々に判定 |
| 論理破損 | 破損したブート領域・管理情報、クイックフォーマット後、消失パーティション |
| 読取不良媒体 | 複数パスによるRAWイメージ取得、読取マップ、限定的再試行、停止・再開 |
| RAID | メンバーイメージからのRAID 0/1/5/6/10・JBODの読み取り専用再構成。対応レイアウトは4.8に限定 |
| 名前・階層 | 残存メタデータから再現。根拠がない場合は不明として扱う |
| シグネチャ探索 | JPEG、PNG、PDF、ZIP、ZIP型Office文書（DOCX/XLSX/PPTX）、MP4/MOV |
| 操作 | GUI、CLI、MCPでイメージ取得・RAID構成・スキャン・検索・選択復元・停止・結果確認 |
| 大容量対応 | ストリーミング読取、ディスク上の索引、途中再開、容量上限のあるプレビュー |
| 出力 | 元の場所、任意ディレクトリー、ZIP。同じ媒体も選択可。機械可読レポート、出力SHA-256 |
| 配布 | 3 OSのインストール版とポータブル版、チェックサム、実画面・技術説明UI、変更履歴、既知の制限 |

復元エンジンは3 OSで同じイメージを使ってテストする。alpha.6からWindows EXE/ZIP、Linux DEB/tar.gz、macOS PKG/.app ZIPを配布する。OS対応と解析できるファイルシステムは別とし、ext4/APFSの直接解析は未対応のまま明記する。

### 3.3 対象の境界と後続拡張

「すべて」は今回指定された対象カテゴリすべてを意味する。
すべてのファイル形式、独自RAID方式、暗号化方式を無条件に復元する意味にはしない。

- FAT12/16、ReFS、Linux/macOSのファイルシステム、Windows Storage Spacesの
  メンバー直接解析、独自のハードウェアRAID配置は後続拡張とする。
- Storage SpacesやハードウェアRAIDがOSに正常な論理ボリュームを公開している場合は、
  対応ファイルシステムの通常の入力として扱える。
- カメラRAW、追加アーカイブ形式、VHD/VHDX/E01、Windows/Linux ARM64は後続拡張とする。macOS arm64はalpha.6の配布対象。
- EFSの復号、WOFなどLZNT1以外の圧縮、鍵のないBitLockerの復号はv1.0に含めない。
- ファイルシステム情報を失った断片化ファイルの再構成は形式ごとに研究し、
  一律の成功保証を設けない。v1.0で必須なのは根拠のあるrunlist・チェーンによる再構成。
- 認識しない物理媒体、ヘッド交換等の物理修理、暗号の突破はソフトの機能範囲外。

対応外の属性や形式を検出した場合は、通常ファイルとして成功扱いせず理由を記録する。
後続機能は別の受入基準を設け、v1.0の達成実績に混ぜない。

## 4. 復元エンジン

### 4.1 入力とソースの識別

- 読取専用ハンドルで開く。エンジンにソースへの書込APIを渡さない。
- セクターサイズ、容量、パーティション範囲、NTFS構造を境界検証する。
- GPTのCRCと代替ヘッダーを検査し、不整合を表示する。
- 512バイト・4 KiBセクターを対象に、デバイスの要求する読取単位を守る。
- 元のディスクID、ボリューム情報、サイズ、選択範囲とサンプルハッシュをセッションに記録する。
- BitLockerはOSで解除済みの論理ボリューム経由で扱う。
  ロックされたソースには解除が必要と表示し、鍵の突破や保存は行わない。
- 管理者権限が必要な読取はWindows用の読取プロセスに隔離する。
  通常のイメージ解析とGUIは一般ユーザー権限で動作させる。

### 4.2 クイックスキャン

NTFSのMFTを解析し、削除済みエントリーを列挙する。
管理情報に基づく復元は、拡張子にかかわらずファイルのバイト列を対象にする。
後述の形式別対応表は、主にシグネチャ探索・形式検証・プレビューに対する制限である。

- レコード署名、USA fixup、属性の長さ、runlist、範囲外参照を検証する。
- FILE_NAMEと親レコードの参照を使い、元の名前と階層を再構築する。
- 親参照のシーケンス番号を照合し、再利用されたレコードとの誤接続を防ぐ。
- resident DATAをMFT内から取り出す。
- non-resident DATAを物理的な断片の順ではなく、論理オフセット順に読み出す。
- 属性リストによる追加レコードを扱い、循環・重複・不正参照を検出する。
- 疎領域と未初期化領域の意味を守り、既存の無関係なディスク内容を混入させない。
- $Bitmap等の割当状況を参考情報として表示する。
  「未割当」は内容の完全性の証明ではなく、「割当済み」も全バイト上書きの証明ではない。
- ハードリンク由来の複数の名前と実データの重複を区別する。
- NTFS圧縮は圧縮単位と疎領域を検証してLZNT1を展開し、展開量を制限する。
- ADSはストリーム名を保持して独立した通常ファイルへ出力する。
  NTFSのストリーム構文を保存先パスとして直接使わない。
- EFS、未対応の圧縮方式、破損ストリームは理由付きで別表示にする。

### 4.3 ディープスキャン

管理情報が不足する場合に、バイト列と形式構造からファイル候補を見つける。

- 検索範囲は、削除データを探す未割当領域を基本とし、全領域も選択できる。
- 未割当判定に使う情報が壊れている場合は、全領域への変更を明示する。
- チャンク境界をまたぐヘッダー・フッターを取りこぼさない。
- ヘッダー一致だけで成功としない。長さ、内部構造、終端、利用可能なCRCを検査する。
- ZIP型Office文書は内容を確認して分類する。
- MP4/MOVはboxの長さと配置を検査する。moovの欠落や断片不明を完全復元と表示しない。
- PDFなど終端や長さが曖昧な形式では、推定範囲と検証の限界を表示する。
- 候補が既存ファイル由来の可能性を持つ場合は、削除済みと断定しない。
- 元の名前・階層を特定できない候補には、形式とオフセットに基づく生成名を使う。
- v1.0のcarvingは連続領域を対象とする。ヘッダーが見つかっただけで、
  メタデータのない断片化ファイルを完全復元できたと表示しない。
- 重複候補や重なる範囲を記録する。根拠なく候補を削除しない。

クイックスキャンの索引を再利用して、必要な範囲だけディープスキャンを実行できる構造にする。

### 4.4 結果の確度

1つの曖昧な「復元可能率」に集約せず、次の状態を個別に保持する。

| 項目 | 状態の例 |
| --- | --- |
| 発見根拠 | 削除MFT、シグネチャ、両方 |
| データ範囲 | 全範囲読取可能、読取失敗あり、範囲不明 |
| 割当との競合 | なし、あり、不明 |
| 形式検証 | 合格、不合格、対象外、未実施 |
| 名前・階層 | メタデータ確認済み、一部推定、不明 |
| 保存結果 | 完了、不完全、失敗、取消 |

「形式検証合格」は削除前のファイルと同一であることを保証しない。
出力ハッシュは以降の同一性確認に使い、削除前の正解ハッシュがない通常利用では
元データとの一致を証明したと表示しない。

### 4.5 FAT32/exFAT

- ブート領域、バックアップ、FAT、ディレクトリエントリーを相互検証する。
- FAT32の長いファイル名はエントリーの連続性とチェックサムを検査する。
  削除によって元の短い名前の先頭文字が不明な場合は、推定部分を区別する。
- exFATはファイル・ストリーム・名前のエントリー集合、割当ビットマップ、
  valid data length、data length、NoFatChainを検証する。
- 残存するクラスターチェーンはループ、範囲外、重複、切断を検出する。
- 削除によりチェーンが失われたファイルの断片位置を捏造しない。
  連続配置の推定と確定情報を分け、形式検証の結果を添える。
- FATが複数ある場合に不一致を隠さず、採用した情報と理由を記録する。
- SDカードやUSBメモリでも消去・TRIM相当処理でデータが消える場合があるため、
  媒体種別だけを根拠に復元可能と断定しない。

### 4.6 消失パーティション、フォーマット、論理破損

- MBR/GPTが失われた場合に、ブート署名、バックアップ、管理構造から領域候補を探索する。
- セクター署名1個だけでパーティションと確定しない。範囲、サイズ、複数の内部構造を検証する。
- 重なる候補や相反するレイアウトは選択候補として残し、自動で元ディスクへ適用しない。
- 見つけた領域を仮想ソースとして扱い、通常のファイルシステム解析へ接続する。
- クイックフォーマット後は、残存する旧メタデータと現行のメタデータを区別する。
- NTFSのMFT断片探索も行うが、$MFTMirrだけで全MFTを再生できるとは扱わない。
- 元のファイルの位置・長さに根拠がない場合は、carving候補として扱う。
- ファイルシステムの修復やパーティションテーブル書換えを復元工程に入れない。

### 4.7 読取不良媒体のイメージ取得

推奨経路は「原媒体 → RAWイメージ＋読取マップ → 解析」とする。
Windowsが読取デバイスとして公開している媒体を対象にする。

- 初回パスで読める範囲を連続取得し、遅延・エラーのある領域を保留する。
- 後続パスで保留範囲を小さく分割する。既定では失敗セクターの追加再試行は最大2回。
- 読取マップは未試行、成功、失敗を別状態にし、ソースID、範囲、時刻、エラーを残す。
- プレースホルダーとして存在するゼロを、ソースから読めたゼロと混同しない。
- 復元エンジンまで読取マップを伝え、欠損と重なる復元物は不完全に分類する。
- 同じソースID・容量・幾何情報の確認後に再開し、既読部分を不用意に再取得しない。
- RAW出力とマップのクラッシュ整合性を保ち、flush済み範囲だけを完了として扱う。
- Rescueで取得したイメージはマニフェストで読取マップと結び付け、
  マップの欠落をエラーにする。外部から渡されたRAWでは取得品質を不明と表示できる。
- 出力先の容量不足や切断時に新しい読取を止め、再開可能なチェックポイントを残す。
- ドライバー内で止まるI/Oの即時取消は保証しない。GUI/MCPは応答を維持する。
- ヘッド制御・ファームウェア変更等の専用ハードウェア操作は行わない。

### 4.8 RAIDの仮想再構成

メンバーのRAWイメージと各読取マップから読み取り専用の仮想ブロックデバイスを作る。
原媒体やコントローラーにRAID設定を書き戻さない。

| 方式 | v1.0の対象と欠損の扱い |
| --- | --- |
| RAID 0 | 通常のストライピング。欠損メンバーに属する範囲は欠損として扱う |
| RAID 1 | 通常のミラー。コピー同士が違う場合は不一致を表示し、正解を自動断定しない |
| RAID 5 | 左右対称・左右非対称の回転パリティ。1メンバー相当の欠損まで再構成可能 |
| RAID 6 | 検証済みのP/Qパリティプロファイル。2メンバー相当の欠損まで再構成可能 |
| RAID 10 | ミラーペアをストライプ化した通常配置。各ペアに有効なコピーが必要 |
| JBOD | 指定順に連結。欠損メンバーの区間は欠損として扱う |

許容欠損数は正常な残存メンバーと整合したパリティを前提にする。
古いコピー、write hole、追加の読取不良があれば、その条件だけで完全復元を保証しない。
RAID 6の配置・GF演算規則、RAID 10の派生配置は互換性表に具体的なプロファイルとして固定し、
テスト済み以外の方式を「RAID 6/10だから対応」と推測しない。

- メンバー順、開始オフセット、ストライプサイズ、パリティ配置、欠損位置を指定できる。
- ストライプサイズはセクターの倍数を要求し、自動探索は4 KiB〜1 MiBを基本範囲とする。
- 自動推定では探索範囲・時間を制限し、複数の候補と根拠を返す。
- パリティ整合だけで正解とせず、ファイルシステムの構造や既知ファイルも照合する。
- メタデータがない場合でも手動で構成でき、設定を再現可能なマニフェストへ保存する。
- 異なるセクターサイズ、容量、欠損状態を検証し、対応できない組合せは理由付きで拒否する。
- 再構成したデータには、どのメンバー・パリティを根拠にしたか追跡できる情報を残す。
- 推定した配列はユーザーが選択してから復元する。推定中に元媒体へ書き込まない。
- 再構成後の仮想ソースに、NTFS/FAT32/exFATの共通エンジンを適用する。

## 5. ソースを保護する入出力

- 保存先は元の場所、任意のフォルダー、ZIPから選ぶ。同じ物理媒体・別パーティションへの保存もユーザーが選べる。
- 同じ媒体への保存は選択データを全て先に読み出してから行う。alpha.8は合計512 MiBまで。超過・確保失敗は出力作成前に停止する。
- スキャン用のセッション・ログ・キャッシュ・一時ファイルは対象媒体へ自動作成しない。結果をメモリーに保持できる。
- 元の場所は再探索した管理情報と確認したマウント先を使う。不明なパスや推定名は指定フォルダーへ保存する。
- 同じ媒体への出力は未選択の削除データへ影響し得ることを表示する。大容量向けの別媒体へのストリーミングも提供する。
- RAIDの再構成・読取マップ等の後続実装では、元メンバーへの直接の書き戻しを禁止する。
- RAWイメージには読取専用でアクセスする。イメージが独立したコピーであり、
  保存媒体自体が復元対象でない場合は、その保存媒体への出力を許容できる。
  同じ入力ファイル・ハードリンクへの上書きは拒否する。
- 既存ファイルを上書きしない。同名は連番を付け、create-newで競合を防ぐ。
- 元の名前を信用せず、絶対パス、親への移動、予約名、ADS構文、reparse pointによる
  出力範囲からの脱出を防ぐ。変換前の名前はレポートに残す。
- 不完全・取消の出力は結果の状態・保存先・書込バイト数で明示する。完了のSHA-256を付けない。従来のストリーミングでは.partialとして残す。
- 読取失敗を黙ってゼロ埋めしない。欠損範囲を記録し、不完全として扱う。
- 取消・クラッシュ時には完成物と処理途中のファイルを区別できるようにする。
- 元媒体の修復、フォーマット、TRIM発行、chkdsk等は復元処理に含めない。

読取専用であることは、本ソフトによる書込を防ぐ意味である。
OSや他のアプリが稼働中のボリュームへ書き込むことまでは止められない。
システムドライブでは、別環境または取得済みイメージを使う手順を案内し、
ライブスキャン結果に「解析中にソースが変化する可能性」を表示する。

## 6. GUI仕様

操作の主経路を「起動 → 入力・保存方式・保存先・詳細検索の設定 → スキャン → 候補の選択 → 復元・結果確認」とする。

alpha.6での確定動作：詳細ビューを既定とし、名前・作成日時・更新日時・種類・サイズ・状態の列を表示する。列見出しで昇降順、境界で列幅を変更する。グループは元フォルダー・種類・作成日・更新日・サイズ・名前の先頭・復元可否。選択は候補IDで保持し、表示・並び順の変更で別のファイルへ移らない。アイコンビューは同じ候補・選択を使う。

詳細検索はQuickのフォルダーパス・深度・拡張子、PNG carvingの開始／終了バイト。深度0は指定フォルダー直下で、未指定なら追加制限なし。結果フィルターと所有領域の検証は分け、Quickは全体の割当確認を続ける。日時が残らない場合は「—」、FATのタイムゾーンが不明なら不明として扱う。既存セッションとの互換性を保つ。

保存先をスキャン前に決める。フォルダー保存は既存の保護を維持し、ZIP保存は一時領域へ復元してからCRC付きZIP64とレポートを作成し、同じ出力先で上書きなしに公開する。失敗・取消は完了と区別し、一時保存場所を残す。

### 6.1 ソース選択

- ディスク、ボリューム、容量、ファイルシステム、接続種別を表示する。
- 物理ディスクとそのパーティションの関係を表示する。
- イメージファイルを選択できる。
- 読取不良媒体ではイメージ取得へ進み、読取マップと残りの失敗範囲を確認できる。
- RAIDはメンバーを追加し、欠損位置・構成候補・推定根拠を確認して仮想ソースを作る。
- 消失パーティションは候補の範囲・形式・整合性を比較して選択できる。
- 作業フォルダー・復元先との競合と、権限不足を開始前に表示する。
- BitLockerのロック状態、対応外の形式を明確にする。

### 6.2 スキャンと候補確認

- 詳細設定でクイック／ディープ、範囲、深度、対象拡張子を選択する。
- フェーズ、読取済み量、候補数、速度、推定残り時間を表示する。
  所要量が不明な段階では、正確な百分率を装わない。
- 停止・取消・セッションからの再開を提供する。
- 名前、拡張子、サイズ、日時、発見根拠、検証状態で検索・絞り込み・並べ替えする。
- 再現できたフォルダー階層と、形式別一覧の両方で選択できる。
- 大量候補をページ単位で表示し、全件をGUIメモリへ読み込まない。
- プレビュー対応はJPEG・PNGと制限付きテキストを初版の必須とする。
  PDF・Office等のプレビューは後続対応。プレビュー非対応と復元非対応を区別する。
- プレビューは隔離プロセスで、メモリ・画素数・処理時間・読取量を制限する。
  スクリプト、マクロ、外部リンクを実行しない。

### 6.3 復元と結果

- 選択件数・合計サイズ・空き容量・保存先を表示して実行する。
- 完了、不完全、失敗、取消を分けて一覧にする。
- エラー理由、保存場所、ハッシュ、処理時間を確認・エクスポートできる。
- 日本語を初期言語にし、英語へ切り替えられる構造にする。
- キーボード操作、High DPI、Windowsのアクセシビリティを受入項目に含める。

alphaではegui/eframeを採用する。Rustとの共通実装とGUIからの復元経路を検証し、
WindowsのIME、アクセシビリティ、大量行表示をv1.0の受入時に確認する。

## 7. CLI仕様

実行ファイル名の案はrescue。GUIと同じ復元エンジン・結果モデルを使用する。

    rescue sources --json
    rescue image --source <source-id> --destination 'E:\Images\disk.raw' --json
    rescue raid inspect --manifest 'E:\Images\array.json' --json
    rescue raid assemble --manifest 'E:\Images\array.json' --work-dir 'F:\RescueWork' --json
    rescue scan --source 'D:\images\disk.raw' --mode quick --work-dir 'E:\RescueWork' --json
    rescue results --session 'E:\RescueWork\<session-id>' --limit 100 --json
    rescue recover --session 'E:\RescueWork\<session-id>' --id <candidate-id> --destination 'E:\Recovered' --json
    rescue resume --session 'E:\RescueWork\<session-id>'
    rescue report --session 'E:\RescueWork\<session-id>' --json
    rescue mcp --stdio --allow-source 'D:\images\disk.raw' --work-dir 'E:\RescueWork' --allow-output-root 'E:\Recovered'

- 上記は引数仕様の案であり、現時点で実行可能なコマンドではない。
- 物理ディスク・ボリュームはsourcesが返す識別子でも指定できる。
- imageはRAWと読取マップを作る。raid assembleは仮想ソースIDを返し、scanへ渡せる。
- scanのモードはquick、deep、partitionとする。partitionは領域候補を列挙する。
- 複数IDは繰り返し指定または選択リストで渡す。全件復元は明示オプションを必要とする。
- --jsonは機械可読出力。標準出力と進捗・診断用の標準エラーを混在させない。
- 長時間操作の--json出力は、バージョン付きNDJSONイベントと最終結果に統一する。
- フィールド名とエラーコードは固定し、表示言語で変えない。
- Ctrl+Cで安全に取消し、再開情報を保存する。
- 非対話利用では確認待ちをしない。保存先・権限等が不足する場合は構造化エラーで終了する。
- 自動化が「候補なし」を障害と区別できるようにする。

終了コード案: 0=処理完了（候補なしも含む）、2=引数・設定不正、
3=権限・保存先制約、4=処理失敗、5=一部失敗／不完全、130=取消。
処理完了は元ファイルとの完全一致を意味しない。

## 8. MCP仕様

ローカルstdioのMCPサーバーを提供する。ネットワーク公開は初期仕様に含めない。
採用する公開MCP仕様の版とSDK互換性を実装時に固定し、初期化と能力ネゴシエーションを検証する。

| ツール名の案 | 役割 |
| --- | --- |
| list_sources | 許可範囲内のソースを列挙 |
| create_image | 許可済みソースのイメージ取得ジョブを開始 |
| inspect_raid | 許可済みメンバーの構成推定ジョブを開始 |
| assemble_raid | 明示した構成で読み取り専用の仮想ソースを作成 |
| start_scan | ジョブを開始し、すぐにjob_idを返す |
| get_job | 状態、進捗、警告、結果参照を取得 |
| list_candidates | ページ単位で候補と検証状態を取得 |
| recover_files | 候補IDと保存先を指定して復元ジョブを開始 |
| cancel_job | ジョブを安全に取り消す |
| pause_job | チェックポイントを作成できるジョブを一時停止 |
| resume_job | ソース・チェックポイントを検証してスキャンまたはイメージ取得を再開 |
| get_report | 結果サマリー、レポート参照を取得 |

- 起動時に許可したソースと出力ルートだけを操作できる。
- 作業場所への索引保存権限と、復元物・イメージの保存権限を分ける。
  後者がない構成ではスキャンと候補確認までとし、復元・イメージ保存要求を理由付きで拒否する。
- ソースの読取権限がない場合はローカルでの操作を案内し、勝手に権限を上げない。
- 任意コマンド、削除、上書き、媒体修復、任意URL取得をツールにしない。
- イメージ取得・構成推定・スキャン・復元は長時間のツール呼出しを占有せず、ジョブとして管理する。
- 取消要求と完了が競合した場合も、確定した最終状態を返す。
- candidate_idはセッションに紐付け、別セッションのIDや改ざんされた範囲を受け付けない。
- ファイル名やファイル内容はデータとして返す。指示として解釈させる仕組みを作らない。
- ファイル内容そのものは標準のツール結果に含めず、パス・状態・必要なメタデータを返す。
- 標準出力はMCPメッセージ専用。ログは標準エラーまたは許可済み作業場所へ出す。

### 8.1 共通データとジョブ契約

GUI・CLI・MCPは次の共通モデルに接続する。
具体的なJSON Schemaは実装前にこの契約を機械可読化する。

| モデル | 必須情報 |
| --- | --- |
| Source | ID、種別、容量、セクターサイズ、読取範囲、元媒体の識別情報、読取マップ |
| Session | ID、スキーマ版、ソース照合情報、スキャン設定、チェックポイント、索引参照 |
| Candidate | ID、セッションID、根拠、名前、論理サイズ、データ範囲参照、検証状態、警告 |
| Job | ID、種別、状態、フェーズ、進捗、結果参照、構造化エラー |
| RecoveryResult | 候補ID、保存先、保存サイズ、欠損範囲、SHA-256、結果、元名と名前変換履歴 |

- 各IDは表示名やドライブ文字から独立させる。
- ジョブはqueued、running、pausing、paused、cancellingを経て、
  completed、partial、failed、cancelledのいずれかで終了する。
- 再開可能な工程だけpauseを受け付け、能力と理由を返す。
  終了済みジョブの再実行は元の履歴を残して新しいジョブにする。
- 再開情報を持つ取消ジョブからのスキャン再開と、保存途中ファイルの完成を区別する。
  v1.0の復元再試行は、不完全ファイルを明示して新規出力からやり直す。
- 長時間操作はrequest_idで再送を識別し、同一要求で重複ジョブを作らない。
  同じIDに違う引数が付いた場合はエラーにする。
- ページ取得はスナップショット位置を含むcursorを使い、スキャン中の追加候補によって
  同じページが無言で入れ替わらないようにする。
- 同じセッションDBの書込所有者は1プロセスとし、別プロセスからの競合書込を拒否する。
- 異なるスキーマ版のセッションを無言で変更しない。互換性を確認し、
  移行が必要なら元データを保った新しいコピーに対して行う。
- エラーはcode、message、retryable、影響範囲を持つ。
  日本語のmessageだけを手掛かりに自動処理させない。

## 9. 共通構成と性能設計

提案するRustワークスペースの責務分割:

- rescue-core: 候補モデル、スキャン、復元、検証、ジョブ状態。
- rescue-io: 読取専用のソース抽象化、イメージ入力、WindowsデバイスI/O。
- rescue-ntfs: NTFS構造・MFT・属性・runlistの解析。
- rescue-fat: FAT32/exFATの管理情報と割当の解析。
- rescue-image: イメージ取得、読取マップ、欠損範囲、再開。
- rescue-raid: 読み取り専用の連結・ミラー・ストライプ・パリティ再構成。
- rescue-partition: MBR/GPT、消失領域の探索、仮想パーティション。
- rescue-carve: 形式ごとの検出と構造検証。
- rescue-session: スキャン索引、再開情報、結果レポート。
- rescue-cli、rescue-gui、rescue-mcp: 入出力と操作フロー。

公開API境界で責務を分け、細かいcrate数は実装時に調整する。
Rustの安定版を正確なバージョンで固定し、Cargo.lockを追跡する。
unsafeはOSとの境界に限定し、必要性と不変条件を文書化する。

- HDDでは連続読取を優先し、同じ媒体へ無秩序に並列シークしない。
- SSDでも読取・検証・索引書込を上限付きキューで接続し、バックプレッシャーをかける。
- 巨大なファイルやディスク全体をメモリへ読み込まない。
- 索引はディスク上に保存し、バッチ更新とページ取得を使う。
- 同じソースのスキャンと復元を同時実行する場合はI/Oを調停する。
- Windowsの権限付き読取プロセスは、起動元と許可済みソースを検証する。
  ローカルIPCにアクセス制御を設け、任意のプロセスへ管理者権限の読取を公開しない。
- 読取不良では再試行回数を制限し、失敗範囲を記録して継続可否を表示する。
- 再開時はソースの同一性と選択範囲を検証する。不一致では自動再開しない。
- サンプル照合は全領域の不変性を保証しない。ライブ媒体では復元直前にも
  必要なメタデータを再検証し、安定したイメージの結果と区別する。

性能目標案:

- 1 TiB、最大1,000万候補の標準評価で、全関連プロセスのピークメモリを合計1 GiB以内。
- 同条件で操作への応答の95パーセンタイルを200 ms以内。
- 通常I/Oが応答する条件では、取消操作から2秒以内に新規読取を停止する。
- 処理中のOS I/Oが停止している場合は「取消待ち」と表示し、完了と偽らない。
- 速度は専用のベンチマークで決める。無条件のMB/sや何倍という宣言はしない。

## 10. 「有料ソフトを上回る」の判定方法

比較対象候補はR-Studio、UFS Explorer、DMDE等。製品名、版、設定、ライセンス条件を
確認して、実際に比較する組合せを確定する。
製品名を挙げるだけでは優位性を主張しない。

### 10.1 評価用データ

正解ファイル、削除前の名前・階層、サイズ、SHA-256を別媒体のマニフェストに保持する。
削除やフォーマットの各操作後にイメージを固定し、全製品へ同じ入力を渡す。
競合製品へ渡す入力と本製品の入力で残存状態を変えない。

ケースには次を含める:

- resident、単一extent、複数extent、属性リスト、疎ファイル。
- 小ファイル、大ファイル、日本語名、長いパス、ハードリンク。
- 削除直後、MFT再利用、部分上書き、完全上書き、読取不良。
- MFTが読める場合と、メタデータが失われたcarvingの場合。
- 512バイト・4 KiBセクター、HDD、SSD。
- 連続領域、断片化、混在した形式、壊れたヘッダーと長さ。
- live NTFSと不変のイメージは別集計にする。
- FAT32/exFATのチェーン残存・消失、exFATの連続配置・断片化。
- クイックフォーマット、消失パーティション、MFT/ブート領域の破損。
- NTFS圧縮、ADS、valid data length、疎領域。
- 読取不良の故障注入、RAWと読取マップの停止・再開・不一致。
- RAIDの各対応レイアウト、正常・欠損・誤った順序・古いコピー・不整合パリティ。

実故障媒体だけでは同条件を再現しづらいため、読取不良は固定したエラーマップでも検証する。
ソフトウェアの評価用に媒体を物理的に破壊しない。

### 10.2 指標

| 指標 | 定義 |
| --- | --- |
| 完全復元率 | 正解と全バイト一致したファイル数 ÷ 対象の削除ファイル数 |
| バイト一致率 | ファイルの論理オフセットを対応付けて一致したバイト数 ÷ 正解総バイト数 |
| 名前再現率 | 元の名前を正しく再現できた対象ファイル数 ÷ 対象数 |
| 階層再現率 | 元の相対パスを正しく再現できた対象ファイル数 ÷ 対象数 |
| 誤検出 | 真のファイルではない候補数、重複候補数を別々に報告 |
| 時間 | スキャン、検証、復元の各時間と合計時間 |
| 資源 | ピークメモリ、CPU、読取量、索引サイズ |

完全復元率は同じファイルの重複出力で増やさない。
部分復元や開けるだけのファイルを完全復元として数えない。
復元不能なケースを後から分母から除外せず、回復可能性を事前に定義したカテゴリでも併記する。
ハッシュで識別できない誤検出は、位置情報と形式検証も使って判定し、不明を明記する。

速度評価は同じマシン・媒体・入力・出力先・検証条件で各3回以上行い、中央値とばらつきを公表する。
キャッシュ有無と読取経路を揃え、製品ごとの必須設定の差も残す。
回収結果の画面表示だけでなく、出力ファイルそのものを採点する。

目標案は、事前に選んだ困難なケース群で最高成績の比較対象より完全復元率を
5ポイント以上改善し、他の必須ケースで退行しないこと。
双方が完全復元率100%のケースでは、その一致率を維持しつつ処理時間25%以上短縮を目標とする。
どちらも未検証の開発目標であり、達成したケースと条件に限って優位性を表現する。
総合で「すべての有料製品を上回る」という無条件の表現は採用しない。

## 11. 品質・受入基準

v1.0の公開条件:

1. 対応範囲の正解付き合成ケースで、期待する全ファイルがSHA-256一致する。
2. GUI、CLI、MCPが同じ入力と設定から同じ候補・復元物を得る。
3. NTFSと形式パーサーが、破損入力で範囲外アクセス、無制限確保、停止不能に陥らない。
4. 中断・再開、電断相当の強制終了、容量不足、アクセス拒否、読取不良を処理できる。
5. 同じ媒体へは全選択データの先行読出し後に保存する。既存ファイルの上書きとパス逸脱を拒否する。
6. イメージの処理前後のハッシュが一致し、デバイス書込APIが使われていないことを確認する。
7. 欠損・未対応・失敗を成功扱いしない。
8. Windows実機またはWindows CIでビルドと統合テストが通る。
9. 実デバイスの管理者読取、UI、アクセシビリティはWindowsの専用試験で確認する。
10. CLIのスキーマとMCPの初期化・列挙・呼出し・取消・権限制約に互換性テストがある。
11. 性能目標を測定し、未達・未測定をリリースノートに明記する。
12. NTFS、FAT32、exFAT、破損媒体、RAIDの全必須カテゴリを検証済みにする。
13. 読取マップの欠損が、解析・パリティ再構成・出力結果まで正しく伝わる。
14. RAID仮想デバイスの出力が、正解となる論理イメージとバイト一致する。
    再構成不能な範囲は欠損として扱う。
15. 既知の制限と対応表が、その版の実装と一致する。

単体・統合テストに加えて、NTFS/形式パーサーのfuzzingとリソース上限テストを行う。
クラウドのLinuxテストだけでWindowsの動作確認済みとはしない。
競合優位の目標未達でも、機能が安定していれば制限を明示して公開できる。
その場合は「有料製品を超えた」という表現を使わない。

## 12. GitHubとリリース運用

- 対象: Xenoah/rescue-deletedfiles_rust。
- 仕様、実装、検証をそれぞれレビューできる変更単位でコミットする。
- 実装の区切りごとにテスト結果を添えてpushする。force-pushは通常運用に含めない。
- 機能がまとまった時点でバージョンを付ける。開発途中はプレリリースにする。
- 実行ファイルは対応するOSとCPUのネイティブビルドで生成する。4ターゲットすべての検証後にインストール版・ポータブル版を公開する。
- CIはfmt、clippy、3 OSのRustテスト、debug/releaseのCLI/MCP統合、35形式の正解照合、パッケージ検査とGUI起動確認を行う。
- タグによる公開処理は、同一コミットの必須検証が通ることを条件とする。
- 全配布物にGUI/CLI、利用手順、対応表、依存ライセンスを含める。
  リリースにはSHA-256一覧、変更履歴、既知の制限を付ける。
- コード署名は配布方針と証明書の用意に合わせて決定する。
  未署名の開発版は未署名と明記し、署名済みと誤認させない。
- ライセンスと外部依存の再配布条件は、最初の配布前に決定・確認する。
- 実ユーザーの復元対象、媒体イメージ、ファイル名を含む個人データはpushしない。
  テストには人工生成または再配布可能な素材を使う。
