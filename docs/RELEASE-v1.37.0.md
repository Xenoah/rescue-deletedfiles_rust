# Rescue v1.37.0

QEMUがディスク識別子（CID）を短い値で書き直したVMDKを読み取れるようになりました。v1.31.0の公開Linuxパッケージ試験で見つかった問題です。公開版が拒否した8つの実イメージを保存し、修正後に各ディスク全体と削除ファイルのバイト列を照合しました。[問題が見つかった公開試験](https://github.com/Xenoah/rescue-deletedfiles_rust/actions/runs/44677087464) · [8イメージの記録](../tests/vmdk-cid/manifest.json)

GUIではVMDKを選び、「元ディスクと照合」に論理ディスク全体の既知の長さ・SHA-256を入力できます。CLIで2つのエクステントから復元した試験の例です。記述ファイルとエクステントはそれぞれ明示的に指定します。

```sh
rescue import-image --image-type vmdk --source volume.vmdk \
  --segment volume-f001.vmdk --segment volume-f002.vmdk --output guest.raw \
  --raw-bytes 2213809152 \
  --raw-sha256 9bb2b942fd942e74adc9edf24e958cf20efebb070293bb05195fefc8696e193c --json
rescue scan --source guest.raw --work-dir scan --json
```

例のハッシュは試験ディスクの値です。手元のVMDKでは、その論理ディスクに対応する値を使います。入力コンテナやエクステントのハッシュは別の値です。

## 復元した原本とディスク境界

WindowsでNTFSから削除したHTML、JSON、RTF、XML、PNG、ZIP、gzipの7ファイルを用意しました。以下の10イメージで、通常スキャンと索引スキャンを別々に実行し、各ファイルの全バイトとSHA-256を削除前の原本と照合しました。10イメージには同じ7原本を使用しています。

| 作成に使ったQEMUと形式 | ゲスト容量 | 照合結果 |
| --- | ---: | --- |
| QEMU 6.2.0、単独flat・単独sparse・分割flat・分割sparse | 各96 MiB | 各形式でディスク全体と7/7ファイルが一致 |
| QEMU 10.0.13、同じ4形式 | 各96 MiB | 各形式でディスク全体と7/7ファイルが一致 |
| QEMU 6.2.0、2エクステントの分割flat | 2,213,809,152バイト | 2 GiBの境界前に3件、境界以降に4件の削除記録。7/7ファイルが一致 |
| QEMU 10.0.13、2エクステントの分割sparse | 2,213,809,152バイト | 同じ境界をまたぐ全バイトと7/7ファイルが一致 |

96 MiBの8例では記述子の終端直後に改行が1バイト残っていました。大容量の2例はQEMUで既存のゼロセクターに同じ値を書いた後、CIDが5桁となり、引用符と改行の2バイトが残った実ファイルです。全例でQEMU自身のディスク比較結果とも一致しました。大容量の両例では2番目のエクステントを省略すると変換を拒否しました。[原本別のSHA-256](vmdk-cid-results.json) · [2 GiB境界とエクステントの実測値](vmdk-cid-boundary-results.json)

GUIでもQEMU 6.2のフラットVMDKと明示指定したエクステントを取り込み、既知のSHA-256と一致したRAWがスキャン元に選ばれました。誤ったSHA-256を指定した場合は出力を作成しませんでした。GUIの通常スキャンから保存したZIP内でも7ファイルの全バイトとSHA-256が原本に一致しました。[GUIの測定値と画面](gui-v1.37-results.json)

## 対応範囲と制限

- 終端後のバイトを受け入れるには、記述子の末尾が数値の `ddb.toolsVersion` 行であること、残ったバイト列がその行の末尾と一致すること、CIDの桁数差で説明できることが必要です。追加の命令、間に空いたゼロ、無関係なバイト列を含む記述子は拒否します。外部記述子と埋め込み記述子のそれぞれで、破損や誤った照合値など12条件を確認しました。
- 既知の長さやSHA-256が合わない場合は未完成のRAWを破棄します。検証値を省略した場合、構造が整ったまま書き換えられたゲストデータを原本と区別するには、別途照合できる記録が必要です。
- 対象の単独・分割VMDK、NTFSの削除記録は内蔵機能で読み取れます。試験ではQEMUの2バージョンで実ファイルを生成し、独立して読み戻しました。VMFSのストレージ、古いCOWD、暗号化または差分親が必要なVMDKには対応する外部ツール・鍵・親のコピーが必要です。上書きされた内容や欠落したエクステントは補えません。
