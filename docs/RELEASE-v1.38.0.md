# Rescue v1.38.0

HDR画像のOpenEXR（`.exr`）を内容から検索し、画像全体が連続して残っていれば復元できます。色、アルファ、深度、オブジェクトIDなどのチャンネルを扱えます。単一画像のほか、左右の視点などを収録したマルチパート画像、複数解像度を持つタイル画像にも対応します。

```sh
rescue scan --source disk.raw --mode carve --extension exr --work-dir scan --json
```

スキャン結果の `session` を指定して `rescue recover --session <session> --all --destination recovered --json` を実行します。GUIではCarvingの拡張子に `exr` を指定し、結果を選んでZIPに保存できます。

## 削除した画像での実測

OpenEXR SDKとFFmpegで作成した27原本をFAT32と4 KiBブロックのext4にそれぞれ書き込み、各ファイルを読み戻してから削除しました。通常スキャンと索引付きスキャンの両方で、各ファイルシステムの27件すべてが削除前のバイト列・SHA-256と一致しました。公式OpenEXRライブラリでも、復元後の各チャンネルの型、寸法、展開した画素のSHA-256を照合しました。[原本と生成方法](../tests/openexr/README.md) · [ファイル別の実測値](openexr-results.json)

| 画像 | 原本数 | 照合した内容 |
| --- | ---: | --- |
| 単一解像度・単一パート | 17 | グレースケール、RGB/RGBA、深度、長いチャンネル名、負の座標原点、行順、複数の圧縮方式 |
| 単一解像度・マルチパート | 5 | ステレオ、切り出し、スキャンラインとタイルの混在、4パート、物理配置が交互になったブロック |
| MIP・RIPタイル画像 | 5 | 8・7・8・49・64レベルの計136通り。独立したC++読取プログラムで各解像度の全チャンネルを照合 |

Linux GUIでFAT32の27ファイルを選択してZIPに保存し、展開した計1,141,953バイトを原本と直接比較しました。HTML・CSVに書き出した結果もZIP内の復元記録に一致しました。[GUIの実測値と画面](gui-v1.38-results.json)

Rustテスト96件、Clippy、統合試験96組が通過しました。35形式・36原本での独立比較は1,116条件すべてが期待結果と一致し、このうち1,016条件で原本と全バイト一致しました。

## 破損と復元できる範囲

- オフセット表と物理位置、パート番号、行・タイル・解像度の識別子を照合し、圧縮された各ブロックを展開します。無効な圧縮、重複や欠落したブロック、逆転した領域など52条件を拒否しました。読み取り不能範囲が画像内にあると復元を拒否し、画像の直後にある場合は原本と一致しました。
- 元画像のコメントを1バイト変更しても画像は正常に展開できます。この変更は、削除前のSHA-256を与えた `match-hashes` で `not_listed` になりました。内容が有効な別画像との区別には原本のハッシュなどが必要です。
- 1 KiBブロックの別のext4でステレオ画像2件を削除した試験では、それぞれ3か所のゼロ領域がスパースホールになり、連続検索では両方とも復元を拒否しました。残っていたファイルシステムの記録をThe Sleuth Kitで読んだところ、2件とも全バイト・SHA-256・画素が一致しました。この場合は `rescue filesystem --source disk.raw --fs-type ext4 --all --destination recovered --json` を使用します。
- 内蔵の内容検索は、非圧縮、RLE、ZIPS、ZIP、PIZ、PXR24、B44、B44Aに対応します。上限はファイル64 MiB、1辺8,192画素、8パート、各16チャンネル、全解像度・全パート合計8,388,608サンプル、65,536ブロックです。チャンネルのサンプリング間隔は縦横とも1が必要です。Deep、DWA、HTJ2K、未対応の属性型、上限を超える画像は対象外です。
- OpenEXR SDKとFFmpegは試験原本の生成や独立検証に使用しました。連続した画像の内容検索はRescue単体で実行できます。断片の並びやスパースホールの位置が失われた画像、上書きやTRIMでデータが失われた画像は、この検索で完全には復元できません。
