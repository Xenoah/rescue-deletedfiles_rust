# Rescue v1.45.0

Linux LVM2の従来型スナップショットから、指定した時点の論理ディスクをRAWへ書き出せます。元のボリュームが上書きされていても、Linuxが保存した変更前のチャンクを使えます。PVのコピーを読み取り、ディスクをマウントせずに処理します。

```sh
rescue lvm-volumes --source disk-a.pv --segment disk-b.pv --json
rescue import-image --image-type lvm2 --source disk-a.pv --segment disk-b.pv --lvm-volume deleted --output historical.raw --json
rescue scan --source historical.raw --mode carve --work-dir scan --json
```

`deleted` はこの試験でつけたスナップショット名です。一覧にある名前またはUUIDで世代を指定してください。既知の論理ディスクの長さとSHA-256があれば、変換時に `--raw-bytes` と `--raw-sha256` で照合できます。

## 削除前・削除後・上書き後の実測

Linux 6.12.107とLVM 2.03.31で3つの独立したボリュームグループを作りました。それぞれでext4上にGIF、JPEG、PDF、PNG 2件、SQLite、WAV、ZIPの8原本を書き、読み戻してから削除しました。削除前と削除後のスナップショットを保存し、その後に元ボリュームの10 MiBを上書きして、大きいPNGだけ別の場所に書き直しました。連結とストライプの両方を元ボリュームと保存領域で試しています。[試験手順とディスク原本](../tests/lvm2-snapshots/README.md)

| 読み出した時点 | 全バイトとSHA-256の照合結果 |
| --- | --- |
| 削除前の3世代 | 各8件が元の名前で存在。The Sleuth Kitの `fls` と `icat` でも原本の全バイトを確認 |
| 削除後の3世代 | 通常・索引スキャンの両方で各8件、延べ24件が原本と一致。`fls` と `istat` で同じinodeの割り当て解除とリンク数0を確認 |
| 上書き後の3つの元ボリュームと、新しく作った1世代 | 各ディスクで独立に再配置したPNGだけが原本と一致 |

この10個の16 MiB論理ディスクは、それぞれLinuxのdevice-mapperから直接読み出した全バイトとSHA-256に一致しました。削除後のext4では元の名前が孤立inodeから失われており、削除ファイルの内容はカービングで回収しました。Ubuntu 22.04用とDebian用のThe Sleuth Kitで独立に同じ結果を確認しました。[ディスク別の実測値](lvm2-snapshot-results.json) · [inodeとハッシュの独立照合](lvm2-snapshot-native-results.json)

Linuxが容量超過により無効にしたスナップショットは、RescueでもRAWを作成せずに拒否しました。同じグループにある正常な世代は読み出せます。別のLinuxゲストで実際に `lvconvert --merge` を実行し、マージ保留中の元ボリュームとスナップショットを両方拒否することも確認しました。さらに、重複チャンク、表の後半の破損、範囲外参照、既知の原本と異なる内容など21条件で拒否を確認しました。

## 利用条件

- グループに属する全PVのイメージを指定してください。対応するのは、通常の連結またはストライプに載った従来型の永続スナップショット（ディスク形式バージョン1）です。保存単位は4 KiB～4 MiB、対応する変更チャンクは1世代あたり最大1,048,576件です。実機相当の試験では4、8、16、32、64 KiBを確認しました。
- 変更前データそのものにチェックサムはありません。構造が正常なまま内容が変わった場合は、元の論理ディスクまたは元ファイルの既知のSHA-256で検出できます。必要なPV、変更前のチャンク、他のコピーをすべて失った場合は、その時点の内容を再構成できません。
- thin、入れ子のスナップショット、ミラー、RAID、cache、マージ途中のグループには、それらに対応したLinux LVM環境が必要です。暗号化された入力には鍵と復号済みPVが必要です。

## GUIでの復元

Linux GUIで2個のPVを指定し、一覧から `history/deleted` を選んで16 MiBのRAWを作成しました。GUIが選択したRAWの全バイトをLinuxの読み出し結果と比較し、新規スキャンから8件をZIPに復元しました。展開した31,236バイトと各ファイルのSHA-256が原本と一致しました。容量超過の `history/exhausted` を選んだ場合は原因を表示し、出力を作成しませんでした。[GUIの実測値と12枚の画面](gui-v1.45-results.json)

Rustテスト96件、Clippy、Linuxリリース実行ファイルの統合試験104組が通過しました。既存35形式・36原本の1,116条件が期待結果に一致し、完全一致を期待した1,016条件すべてで原本と一致しました。
