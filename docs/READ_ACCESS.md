# Windowsの読取権限分離

alpha.16開発版。GUIは「ディスクの読取を許可」、CLIは
`--request-read-access` を明示したときだけWindowsの許可画面を起動する。
CLIの例は `rescue --request-read-access scan --source \\.\PhysicalDrive1 --work-dir D:\Rescue --indexed --json`。
復元、プレビュー、イメージ取得、探索にも同じ指定を使える。
MCPの要求からUACを起動する経路はない。

## 権限と通信

1. 通常のプロセスが要求ごとにUUIDを生成し、ローカル専用・単一インスタンスの名前付きパイプを作る。
   DACLは要求者、Administrators、SYSTEMだけを許可する。
2. 自分と同一の実行ファイルを`runas`で起動する。ディスク名はコマンドラインに渡さず、認証後のパイプで渡す。
3. 両側が相手のPIDと実行ファイルのファイルIDを確認する。補助プロセスは起動元の作成時刻とWindowsセッションも照合する。
   接続先に管理者トークンを偽装利用させないよう、クライアント側SQOSをIdentificationに制限する。
4. 補助プロセスが受け付けるのは正規化した物理ディスク、ドライブボリューム、Volume GUIDだけ。
   通常ファイル、UNC、名前付きパイプ、デバイス配下のパスは許可しない。
5. 読取専用で開いたハンドルを通常プロセスへ渡す。受取側は`NtQueryObject`で実際のアクセス権を調べ、
   データ書込、追記、属性/EA書込、削除、DACL/所有者変更のいずれかがあれば拒否する。
6. 通常プロセスが自分の読取ハンドルを複製して受領応答を返す。補助プロセスは受渡し用ハンドルを閉じて終了する。
   正常終了を確認してからスキャンを始める。ファイルシステム解析、復元先の作成、デコードを昇格させない。

フレームは4 KiB、IPC待機は30秒、プロセス内で保持する読取先は最大16。
UACのユーザー操作時間はIPC待機とは別に扱う。取消後にWindowsの許可画面が残る場合は、その画面も閉じる。
ディスクI/O自体がOS内で停止する場合は、IPCタイムアウトだけで補助プロセスの終了を保証できない。

## プレビューへの継承

読取を許可したディスクのプレビューでは、親が自分の子プロセスに限って読取ハンドルを複製する。
子側もアクセス権とディスク種別を再検査する。RAIDは当該セッションのメンバーだけが対象となる。
MCPのソース許可リストも子に引き継ぎ、再帰的なメンバー参照にも適用する。
ディスクの並行読取は明示オフセットを使用し、複製ハンドル間の共有ファイル位置に依存しない。

これはWindowsでの実行結果ではない。`scripts/e2e_read_access_native.py`をWindowsネイティブVMへ追加し、
新規作成した読取専用VHDで、実補助プロセス、読取権限、終了、全36ファイル、プレビュー3形式、全ディスク取得を検証する。
