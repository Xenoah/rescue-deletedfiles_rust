# Windowsの読取権限分離

alpha.16開発版。GUIは「ディスクの読取を許可」、CLIは
`--request-read-access` を明示したときだけWindowsの許可画面を起動する。
CLIの例は `rescue --request-read-access scan --source \\.\PhysicalDrive1 --work-dir D:\Rescue --indexed --json`。
復元、プレビュー、イメージ取得、探索にも同じ指定を使える。
MCPの要求からUACを起動する経路はない。

## 権限と通信

1. 通常のプロセスが要求ごとにUUIDを生成し、ローカル専用・単一インスタンスの名前付きパイプを作る。
   DACLは要求者、Administrators、SYSTEMだけを許可する。
2. 同じ実行ファイルから一時的な受取プロセスを通常権限で起動し、専用の`KILL_ON_JOB_CLOSE` Job Objectに所属させる。
   所属を確認してから要求を送る。受取プロセスが同じ実行ファイルを`runas`で起動する。
   ディスク名はコマンドラインに渡さず、認証後のパイプで渡す。
3. 両側が相手のPIDと実行ファイルのファイルIDを確認する。補助プロセスは起動元の作成時刻とWindowsセッションも照合する。
   接続先に管理者トークンを偽装利用させないよう、クライアント側SQOSをIdentificationに制限する。
4. 補助プロセスが受け付けるのは正規化した物理ディスク、ドライブボリューム、Volume GUIDだけ。
   通常ファイル、UNC、名前付きパイプ、デバイス配下のパスは許可しない。
5. 読取専用で開いたハンドルを一時的な受取プロセスへ渡す。受取側は`NtQueryObject`で実際のアクセス権を調べ、
   データ書込、追記、属性/EA書込、削除、DACL/所有者変更のいずれかがあれば拒否する。
6. 受取プロセスが読取ハンドルを複製して受領応答を返す。昇格した補助プロセスは受渡し用ハンドルを閉じて終了する。
   その後、GUI/CLIが自分の通常権限の子から読取ハンドルを複製し、容量・セクター・媒体IDと権限を再検査する。
   両方の子の正常終了を確認してからスキャンを始める。ファイルシステム解析、復元先の作成、デコードを昇格させない。

レビューで、昇格側がハンドル複製直後に強制終了するとデストラクターが実行されず、従来方式ではGUI/CLIに
未回収のハンドルが残る問題を見つけた。一時プロセスを介する方式では、その未回収ハンドルも受取側の終了で閉じる。
GUI/CLIが強制終了した場合も専用Jobの終了規則を使う。通常プロセスへ昇格側の`PROCESS_DUP_HANDLE`を
許可する方式は、昇格したトークン等の複製を許してしまうため使わない。

フレームは4 KiB、IPC待機は30秒、プロセス内で保持する読取先は最大16。
UACのユーザー操作時間はIPC待機とは別に扱う。取消後にWindowsの許可画面が残る場合は、その画面も閉じる。
ディスクI/O自体がOS内で停止する場合は、IPCタイムアウトだけで補助プロセスの終了を保証できない。

## プレビューへの継承

読取を許可したディスクのプレビューでは、親が自分の子プロセスに限って読取ハンドルを複製する。
子側もアクセス権とディスク種別を再検査する。RAIDは当該セッションのメンバーだけが対象となる。
MCPのソース許可リストも子に引き継ぎ、再帰的なメンバー参照にも適用する。
ディスクの並行読取は明示オフセットを使用し、複製ハンドル間の共有ファイル位置に依存しない。

## 検証状況

[Windows実行](https://github.com/Xenoah/rescue-deletedfiles_rust/actions/runs/42143341945)は、管理者の親プロセスの6条件と、
実UAC分離トークンを持つ通常権限の親プロセスの8条件を通過した。
新規作成した読取専用64 MiB VHDで、許可前のアクセス拒否、実補助プロセスの終了、
全36ファイルの復元、プレビュー3形式、全ディスク取得、元媒体の不変を検証した。
`parent_elevated=false` と実際のハンドル権限を各操作で確認する。

CIのサービスログオンには通常のUAC-linked tokenがないため、使い捨てVM内に専用アカウントを作り、
対話ログオンによる分離トークンが非昇格・中整合性・`TokenElevationTypeLimited`であることを確認する。
試験中だけ、その専用アカウントへデスクトップ権限を付与し、終了後に元のACLをバイト照合して復元する。
専用アカウントは削除し、UACポリシーも元に戻す。パスワードは試験プロセスのメモリー内だけで扱う。
これは実Windowsトークンによる処理の検証であり、利用者が許可画面をクリックした試験ではない。

実行中に三つの製品不具合を修正した。

- 非同期パイプの待機で、Win32の `ERROR_NO_DATA` と切断を区別する。実際の遅延フレームと切断をWindowsで検証した。
- セクター情報は `IOCTL_DISK_GET_DRIVE_GEOMETRY`、容量は独立した長さの問い合わせで取得する。
  読取可能なVHDで、拡張ジオメトリとパーティション情報だけがエラー1117になることを独立したWin32呼出しで確認した。
- 保存先やマウント先の構成確認には、データ読取権限を要求せず、アクセス権0のハンドルと `FILE_ANY_ACCESS` の照会を使う。
  このハンドルでは元データの読み書きを行わない。選択ソースの読取許可と、保存先の識別を区別する。

Windows向けの型検査・Clippyも実施済み。一時受取方式の追加試験は、テスト専用プロセスを実際に強制終了し、
未通知ハンドルでロックされたテストファイルが受取側の終了後に削除可能になることを調べる。
親の強制終了によるJobの終了、PID・作成時刻の相違、不正フレーム・途中切断・待機中の取消も対象にした。
これらのネイティブ実行結果は追記予定。上記の既存VHD合格記録と新方式の合格記録を混同しない。
通常権限のGUI、対話的UACの許可・拒否の追加検証も残っており、v1.0受入完了ではない。
