# Rescue v1.48.0

ext2・ext3のディスクで、現在使用中の領域を除いて削除ファイルを探せます。未使用と記録されたブロックを検索し、候補全体が使用中のブロックに重なっていないかを復元時にも確認します。Linuxで作成したディスクをWindows、macOS、Linuxから読み取るための内蔵機能です。

```sh
rescue scan --source linux-disk.raw --mode carve --carve-scope unallocated --work-dir scan --json
rescue recover --session SESSION --all --destination recovered --json
```

ext2・ext3の従来のブロックビットマップにはチェックサムがありません。Rescueはグループごとの空き数とファイルシステム全体の空き数を照合します。管理領域に加え、使用中の全inodeから直接・1段・2段・3段間接ブロックをたどり、再構成した使用領域と割り当てマップが一致することを確認します。ext3では内部ジャーナルに未反映の記録がないことも確認します。状態が確定できない場合は `ALLOCATION_FALLBACK` を記録し、割り当て状態を「不明」として検索します。

## Linuxでの削除と復元

Linux仮想マシンの各ボリュームに、BMP、GIF、JPEG、PDF、PNG、SQLite、WAV、WebP、ZIPを2組ずつ書き込みました。両組を読み戻してから片方だけを削除し、通常スキャンと索引スキャンで復元しました。下表の各件について原本の全バイトとSHA-256を照合しました。[実証用ディスクとファイルの位置](../tests/legacy-ext/manifest.json) · [Linuxの検証記録](legacy-ext-native-results.json)

| ディスク構成 | 原本と一致した削除ファイル | 除外した同一内容の使用中ファイル |
| --- | ---: | ---: |
| ext2、1・2・4 KiBブロック | 27件 | 27件 |
| ext3、1・2・4 KiBブロック | 27件 | 27件 |
| ext2 revision 0、1 KiBブロック | 9件 | 9件 |
| ext3、3段間接ブロックを使うスパースファイルを併設 | 9件 | 9件 |
| **合計** | **72件** | **72件** |

全領域検索では両組を検出しました。2 KiBのext2とext3は、それぞれ論理セクター512バイトと4 KiBのGPTディスクの中でも検証しました。Sleuth Kitで使用中の9本を読み戻し、削除済み・使用中の各ファイルが占める全ブロックの割り当てを照合しました。約68 MiBのスパースファイルは、実際にLinuxが確保した直接・1段・2段・3段間接ブロックのすべてを含みます。ハードリンクと、inode内・外に保存されるシンボリックリンクも同じボリュームに存在します。[再現手順](../tests/legacy-ext/README.md)

空きブロック数を保ったまま使用中と未使用のビットを交換した例、割り当てマップが未読の例、ジャーナルの再生が必要な例、間接ブロックが循環する例など49条件で、確定できない状態を「不明」としました。使用中のWAVの2番目のブロックを同じ内容の削除済みWAVに実際に再割り当てした試験では、保存済みセッションの復元が `SOURCE_CHANGED` で停止し、出力ファイルを作りませんでした。[通常・索引スキャンの検証記録](legacy-ext-results.json)

GNU Partedで作成した4,320,133,120バイトのGPTディスクにも、検証済みのext3を配置しました。パーティションの開始位置は4,288,129,024バイトで、削除済みWAVのデータは4 GiBの前後にまたがります。9本すべてが通常・索引スキャンで原本と一致し、対象範囲の前後でディスク全体のSHA-256も一致しました。これは同じ9本を異なるディスク配置で再検証した結果です。[GPT原本とSHA-256](../tests/legacy-ext/gpt-4g/manifest.json)

GUIの新規スキャンからext3で削除した9本をZIPへ復元し、展開した22,126バイトを原本と照合しました。復元時に再検証した割り当て状態が、フォルダー出力・ZIP出力の両方のレポートに反映されます。公開版v1.37.0では、ext4の7本を正しく復元してもレポートの割り当て欄が「不明」に戻っていました。今回のビルドは同じ7本を両出力で「未割り当て」と記録しました。全領域検索を選んだ場合は引き続き「不明」と記録します。[GUIの記録](gui-v1.48-results.json) · [公開版との比較](legacy-ext-export-comparison.json)

Linuxでは統合テスト108組とRustテスト96件が通過しました。別のファイル形式コーパス1,116件もすべて期待値どおりで、原本が完全に残る1,016件は全バイトが一致しました。Sleuth Kit 4.11.1と4.12の両方で同じext2・ext3検証結果を得ました。

## 復元できる条件

対象は、クリーンにアンマウントしたLinuxのext2 revision 0・1と、クリーンな内部ジャーナルを持つext3です。ブロックサイズ1・2・4 KiB、従来のグループ記述子とinodeブロックマップを扱います。メタデータの読み込み量を制限しているため、32 MiBを超える割り当てビットマップ、16,384グループ超、使用中inodeが262,144を超えるボリュームなどでは割り当て状態を「不明」とします。

空き領域の検索で復元できるのは、対応形式の連続したファイルです。元のファイル名や削除時刻は判定できません。断片化したファイルや識別子を持たない形式は、有効なファイル配置情報が残っていればSleuth Kitを使う `rescue filesystem` から復元を試せます。上書き済みの内容や、読み取れない元データは戻せません。
