# 永続索引とスキャン再開（実装中）

この工程はまだ公開版ではない。現在はNTFS/FAT32/exFATクイックスキャンと署名探索のCLI/MCP経路を実装し、
残存MFT・GUIにも接続済み。大規模評価と公開実物の検証を続けている。
v1.0の必須範囲はSPEC.mdとV1_ACCEPTANCE.mdを保持する。

候補はSQLiteのディスク索引へ追記する。最大128候補または16 MiBのバッチと、
ボリューム・MFTレコード・ストリームの再開位置を同じトランザクションで確定する。
WALとsynchronous=FULLを使い、電源断の実際の耐性はOS・ストレージの同期保証に依存する。
NTFSの親フォルダーは最大4096件のキャッシュと256階層の循環検査で解決し、全候補は保持しない。
読取り元の識別情報・容量・指紋・選択領域を再検証し、不一致では自動再開しない。
ライブ媒体のサンプル指紋は全領域不変の保証ではなく、復元前に候補の管理情報を再検証する。

ページは最大1000件/32 MiB。カーソルは索引ID、候補追加の上限位置、検索条件のダイジェスト、
並替えキーと連番を含む。取得開始後に追加された候補はそのページ列へ混入しない。
名前・パス・サイズ・作成/更新日時・種類・状態で並替え、別名を含めて検索できる。
日付のタイムゾーンが不明なものへUTCを付加しない。

書込み所有者はOSのファイルロックで1プロセスに制限する。読取りは同時に可能。
所有者ファイルを終了時に削除しないため、再起動時に別のinodeをロックして競合する問題を避ける。
未知の索引スキーマは変更せず拒否する。旧JSONは新しい索引へコピーし、原本を保持する。
SQLite拡張の動的ロードは使用せず、trusted_schema、トリガー、ビューを無効化する。
キャッシュは8 MiB、mmapなし、作業領域はファイル、SQL・行・バッチに上限を設ける。

```sh
rescue scan --indexed --source disk.raw --work-dir work --progress --json
rescue results --session work/ID.rescue-index/session.sqlite --sort size --limit 100 --json
rescue resume --session work/ID.rescue-index/session.sqlite --progress --json
rescue recover --session work/ID.rescue-index/session.sqlite --id mft-20-7 --archive files.zip --json
rescue index-import --session old.rescue-session.json --work-dir work --json
```

MCPはstart_scanのindexed、pause_job、resume_job、open_sessionと安定したlist_candidatesを提供する。
索引の再読込は設定済みの作業領域内に限り、元ソースの許可が必要。
復元時は選択行だけを読み、既存の先行読取り・元データ照合・保存先制約を通す。
同一媒体へ作業索引を書かない制約は、元の場所へのメモリー内復元とは別に維持する。

保存層7項目を含む43コアテストとGUI10項目が通過した。GUIでは1,256候補を500件のページで表示し、
3ページから選んだ4件のZIP内容を正解データと照合した。183候補での中断から1,256候補へ再開し、
選択IDを保持した。開発ビルドでの確認であり、公開パッケージの検証は別に行う。
従来の18統合群も復元処理の変更後に通過した。FTS追加後の19群と大規模測定は進行中。

署名探索も1 MiB窓と候補のバッチで確定し、次のバイト位置、検証回数、残り検証量、
ZIP内部レコードの抑制位置を保存する。再開で検証予算をリセットしない。
既存の形式検証器を共用し、正常・破損・窓境界・ZIP内の別ZIP・強制終了・変更済みチェックポイントの
65条件を通過、60ファイルをバイト照合した。キャンセル中の未確定窓は再検査する。

FAT32/exFATはディレクトリーの位置、長い名前の連続エントリー、フォルダー待ち行列、
使用中の割当範囲と検証予算を保存する。候補原本はSQLiteへ一時保存し、
使用中ファイルとの重複を検査してから公開候補へ追記する。未確定の所有関係を
「復元対応」として途中表示しない。強制終了時は未確定の最大256スロットを再検査する。
階層数・クラスタ検査量等の既存上限と、32 MiBのチェックポイント上限を適用する。

残存MFT探索は現在のMFT列挙後に独立したバイト位置・レコード内ストリーム位置へ進む。
レコード検証量（256 MiB/ボリューム）と試行数を引き継ぎ、現在のMFTが壊れた場合も
検証済みブートの範囲で探索する。旧データの名前・元階層・削除状態は確定しない。
4 MiB境界のレコード、ADS、強制終了、予算保持、不正カーソル、MCP停止/再開の8条件と、
既存破損コーパスの4比較を通過し、13ストリームをバイト照合した。

NTFS保存基盤は [42020381318](https://github.com/Xenoah/rescue-deletedfiles_rust/actions/runs/42020381318) で
全4ネイティブVMを通過。FAT接続後のLinux全17統合群・40コアテスト・Clippyを通過した。
今回の残存MFT接続以降の全体結果は次の記録で区別する。

索引スキーマ2以降は種類・状態の並替えと、元フォルダー・種類・日付・サイズ・名前の先頭・状態による
グループ化に対応する。カーソルはグループ・不明値の順位も保持し、日時のUTC/ローカル不明を
混同せず、不明な日時/サイズを昇降順とも末尾に置く。検索SQLは2秒の実行予算で中断し、
GUIスレッドとは分離する。これは応答200 msの目標達成を意味せず、大規模測定は別途記録する。
`rescue index-import` は旧JSONとSQLiteスキーマ1/2/3を新しい索引へコピーする。
探索位置・未検証のFATエントリー・再開可否を保持し、元DBを書き換えない。
ファイル形式は拡張子に依存せずヘッダーで識別する。

GUIはデータベース検索を別スレッドで行い、1ページ500件だけを保持する。
ソート・グループ・検索が変わるとページ列を開始し直す。ページ間の選択はIDとサイズだけで保持し、
未表示の候補を選択したまま復元できる。結果が切り替わる途中は古い行の選択を止める。
`rescue-gui --session session.sqlite` で保存した索引を開ける。
安全な作業先を用意できるフォルダー/ZIP保存では索引を自動利用する。
元の場所への復元で作業先がない場合は、従来のメモリー内探索とその上限を使う。

復元前の全候補を保持する再スキャンを廃止した。NTFSは選択レコードと親参照を直接検証し、
FAT32/exFATは使用中の割当とディレクトリーの走査を続けながら選択したエントリーだけを保持する。
保存済みの名前・サイズ・階層を信頼せず、元データから取得し直す。署名/残存MFTも対象位置を再検証する。
各FSで100,010件より後の候補、NTFSでは200万レコードより後の候補をCLIとMCPで復元し、
6出力と元イメージの全バイトハッシュを照合した。これは合成イメージでの検証である。

スキーマ3は3文字単位のFTS5索引を追加した。入力はSQL/FTSの命令として扱わず、
リテラルの3文字列へ分解して候補を絞る。最後に元の検索文字列の部分一致を検査する。
日本語・引用符・記号・結合文字・長い検索・短い検索の一致と、スキーマ2からのコピー移行を検証した。
検索時間の目標達成は大規模測定結果で判断する。
