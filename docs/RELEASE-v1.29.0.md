# Rescue v1.29.0

Mac OS拡張（HFS+）と、大文字・小文字を区別するHFSXで、現在空いているブロックからファイルを検索できます。GUIで「Carving」と「未割当領域」を選ぶと、使用中のブロックを一部でも含む候補は除外されます。CLI・MCPも同じ割当情報を使います。この検索に外部ツールは不要です。

```sh
rescue scan --source mac-volume.raw --mode carve --carve-scope unallocated --work-dir scan --json
```

## macOSで削除したファイルの検証

macOS標準の `newfs_hfs` で32 MiBのディスクを4個作成しました。それぞれにBMP、GIF、PNG、PDF、WebP、WAV、ZIPを保存して読み戻し、同じ内容のコピーを別の場所に残して元の7件を削除しました。

| ファイルシステム | 内部ジャーナル | 削除したファイルの全バイト・SHA-256一致 | 検索から除外した現存コピー |
| --- | --- | --- | --- |
| HFS+ | なし | 7/7 | 7/7 |
| HFSX | なし | 7/7 | 7/7 |
| HFS+ | あり、正常にアンマウント | 7/7 | 7/7 |
| HFSX | あり、正常にアンマウント | 7/7 | 7/7 |

通常スキャンと索引付きスキャンで照合し、全領域検索では現存コピーも同じ原本ハッシュで見つかることを確かめました。APMおよび4 KiBセクターのGPT内でも削除した7件を復元しました。LinuxではThe Sleuth Kitの `fls` と `blkstat` を使い、現存ファイルの一覧と、各ファイルが占めたブロックの現在の割り当てを照合しました。[原本・ディスクのSHA-256と破損試験](hfs-allocation-results.json) · [macOSでの生成記録](https://github.com/Xenoah/rescue-deletedfiles_rust/actions/runs/44655883383) · [ジャーナル付きの生成記録](https://github.com/Xenoah/rescue-deletedfiles_rust/actions/runs/44657135277)

Linuxの実GUIではHFS+の7件、計13,167バイトをZIPへ復元し、各エントリの全バイトとSHA-256を原本と照合しました。入力ディスクのSHA-256は処理前後で一致しました。[画面とGUIの検証記録](gui-v1.29-results.json)

Rustテスト96件、厳格なClippy、統合試験87組が通過しました。35形式・36原本の比較では、上書きや破損を含む1,116条件のうち1,016条件で原本と完全一致し、全条件で期待した結果になりました。

## 判定できる範囲

- 対象はHFS+バージョン4とHFSXバージョン5です。主・予備ボリュームヘッダー、ビットマップの空き数、管理ファイルと予約領域の割り当てを検査します。内部ジャーナルがある場合は、位置、サイズ、ヘッダーチェックサムと未反映トランザクションの有無も検査します。
- 破損、読み取り不能、外部ジャーナル、ジャーナル再生が必要な場合は、割り当てを「不明」と表示して読める範囲を検索します。この場合は現存ファイルも候補に含まれます。元の媒体への書き込みやジャーナル再生は行いません。
- ビットマップは32 MiBまで、割当ファイルの配置はボリュームヘッダーに格納された8個のエクステントまで扱います。それ以上の配置やClassic HFSでは割り当てを検証できません。
- 内容検索の対象は対応形式の連続して残ったファイルです。削除前の名前、フォルダー、リソースフォーク、断片化した配置はこの機能の対象外です。上書き・TRIMで失われた内容には別のコピーが必要です。
- 2ブロックにまたがるWAVの後半だけが再割り当てされた試験では、候補から除外しました。保存済みセッションからの通常復元とストリーミング復元も、原本と同じバイトが残っていても出力を拒否しました。
